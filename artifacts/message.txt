Refuse a registry match outside the project's worktrees-dir

A `:lite` session's worktree is a symlink to the project checkout, so
it canonicalizes to the checkout root — a path that prefixes every
worktree the project owns and is identical for every lite session
running at once. session-from-cwd matched such an entry on prefix
alone, so the bare ~/Code/brian and ~/Code/nido checkouts, and
everything under them, each resolved to a session picked arbitrarily
from the ones that tied, under a name that escaped the worktrees-dir
it was relativized against: 10 of the 19 live registry entries answer
to ".." or "../nido".

Such a name keys no workstream, no state dir and no session home, so
every write made under it lands nowhere and reports success — each
caller's when-let sees a truthy map and passes. It cost one review run
all four of its ledger writes, the parked finding that was its only
handover to a human among them. worktree-from-cwd inherits the answer
and review:loop uses it to CHOOSE the tree to review, so a loop
started at a checkout root reviews a worktree somewhere else.

Containment is asked of each candidate rather than of the winner: an
entry whose canonical path is not under its project's worktrees-dir is
not a match at all, so a lite entry steps aside instead of outranking
the real worktree an agent stands in. Rejected: rejecting the derived
NAME after the match. It answers one step too late — a lite entry that
won would null the whole resolution rather than yield — and it treats
".." as a spelling rather than as what it means.

Layer: behavioral

Claims: a registry entry canonicalizing outside its project's
  worktrees-dir never resolves a cwd, so session-from-cwd is nil
  rather than wrong wherever it cannot name the session the caller
  stands in.
Verify: bb nido:test — the two lite-worktree cases fail on the parent
  revision, naming ".." and "../nido"; the third holds a real worktree
  resolving while a lite entry is registered beside it.
Lane: none
Out of scope: reaching a lite run's own workstream at all. Its cwd
  canonicalizes to the shared checkout, so the identity is gone before
  nido sees it and no derivation can recover it — FU-93 carries the
  alternative, which is to carry the coordinates rather than derive
  them.
